# HalcyonA2

Visual Studio project for the A2 / Orion Drift private-server DLL — the payload that flips the
retail client into a listen/dedicated server and patches the pieces the shipping build compiled
out. `HalcyonA2\dllmain.cpp` is the reference implementation from `code.txt`, unmodified.

Built and verified against:

| | |
|---|---|
| Game binary | `AnotherAxiom-A2-Rift\A2\Binaries\Win64\A2-Win64-Shipping.exe` (166 MB, 2024-11-05) |
| Engine | Unreal Engine **5.4.2**, build **20996** (`5.4.2-20996+++A2+Release-A2`) |
| SDK | Dumper-7 v7.0.1 |
| Toolchain | VS 2022 (v143), Windows SDK 10.0.26100, C++20, x64 |

> **The offsets in `dllmain.cpp` are build-specific.** Every `*_RVA` constant, every
> `WriteByte(base + ...)` patch and every hardcoded member offset was reversed from *this*
> `A2-Win64-Shipping.exe`. A different game build needs all of them re-derived — a fresh SDK
> dump alone will not fix them.

## Prerequisites

- Visual Studio 2022 with **Desktop development with C++** (MSVC v143 + Windows 10/11 SDK).
- 64-bit Python 3.9+ — only if you want `tools\inject.py` instead of `tools\Inject.ps1`.

## 1. Generate the SDK and mappings

The SDK is *not* checked in: it is generated from the game binary, and it must match the exact
build you run against.

```powershell
cd tools
.\Get-Dumper7.ps1        # optional: refresh Dumper-7 to the latest release
.\Dump-A2.ps1
```

`Dump-A2.ps1` follows the documented Dumper-7 flow:

1. Writes a **global** profile at `C:\Dumper-7\Dumper-7.ini` (`SleepTimeout`, `DumpKey=F8`) so
   the dumper waits for the engine to finish coming up instead of dumping the instant it loads.
   Nothing is written into the game install.
2. Launches `A2-Win64-Shipping.exe` with `-nullrhi -nohmd -nosound -unattended -nosplash -log`
   — the same headless mode the server runs in. Game stdout/stderr land in `tools\logs\`.
3. Waits for engine init, then injects `Dumper-7.dll`.
4. Waits for `C:\Dumper-7\<GameVersion>-<GameName>\` to fill in, then installs:
   - the whole `CppSDK\` (`SDK.hpp`, `SDK\`, `PropertyFixup.hpp`, `UnrealContainers.hpp`,
     `UtfN.hpp`, `NameCollisions.inl`, `Assertions.inl`) → `HalcyonA2\HalcyonA2\`
   - `Mappings\*.usmap` → `tools\Mappings\`
5. Runs `Fix-SDK.ps1` (see below).

The raw dump — `GObjects-Dump.txt`, `GObjects-Dump-WithProperties.txt`, `IDAMappings\`,
`Dumpspace\` — stays in `C:\Dumper-7\` for reference.

Useful switches:

```powershell
.\Dump-A2.ps1 -AttachOnly                  # game already running (e.g. launched with a headset)
.\Dump-A2.ps1 -InitWaitSeconds 90          # slow box / cold cache
.\Dump-A2.ps1 -UseExistingDump 'C:\Dumper-7\5.4.2-20996+++A2+Release-A2'   # reinstall, no relaunch
```

### Why Fix-SDK.ps1 exists

Dumper-7 de-duplicates Blueprint member names (`Foo`, `Foo_0`, `Foo_1`…), but the mangling can
still emit two members with the same C++ identifier in one struct. On this build that happens
once, in `BP_VRPawn_parameters.hpp`: two `Temp_real_Variable_1` at `0x90` and `0x98`. That is a
C2086 redefinition, and since one member then disappears, every offset `static_assert` in the
struct fails as well.

`Fix-SDK.ps1` renames the later occurrences to `<name>_dupN` in the struct body **and** in the
matching `static_assert` in `Assertions.inl` (matched by position, so each assert keeps checking
the offset it was generated for). Types and offsets are untouched, so the layout still verifies.
It is idempotent and runs automatically after each dump; `-WhatIfOnly` reports without writing.

## 2. Build

```powershell
cd tools
.\Build.ps1                      # Release|x64 -> build\x64\Release\HalcyonA2.dll
.\Build.ps1 -Configuration Debug
.\Build.ps1 -Rebuild
```

Or open `HalcyonA2.sln` in Visual Studio and build `Release|x64`. Both configurations build with
**0 errors, 0 warnings**.

Project settings that matter:

- **Static CRT** (`/MT`, `/MTd`) — the DLL is injected into a process with no VC++ redist guarantee.
- **`/std:c++20`, `/bigobj`** — the generated SDK needs both.
- **`/EHsc`** — `dllmain.cpp` is written so no `__try` function holds an unwinding object (C2712).
- `WIN32_LEAN_AND_MEAN` / `NOMINMAX` are set **only** in `pch.h` (guarded), never on the command
  line: the generated `SDK\Basic.hpp` defines them itself, which would make every SDK translation
  unit warn C4005.
- `SDK\**\*.cpp` is globbed rather than listed, so a re-dump needs no project edit. All 204
  generated sources are compiled, so any SDK function the payload calls is guaranteed to link.
- MinHook is compiled from vendored source (`ThirdParty\MinHook`), not linked as a prebuilt `.lib`.

## 3. Inject

```powershell
# PowerShell
.\tools\Inject.ps1 -ProcessName A2-Win64-Shipping -DllPath .\build\x64\Release\HalcyonA2.dll

# Python (same technique, standalone)
python tools\inject.py --process A2-Win64-Shipping.exe --dll build\x64\Release\HalcyonA2.dll
python tools\inject.py --list A2                       # find a pid
python tools\inject.py --process A2-Win64-Shipping.exe --dll ... --wait 120 --delay 45
```

Both do `OpenProcess` → `VirtualAllocEx` → `WriteProcessMemory` (UTF-16 path) →
`CreateRemoteThread(LoadLibraryW)` → wait → `VirtualFreeEx`. Run elevated if the target is
elevated. 64-bit host only.

`dllmain.cpp` never works in `DllMain` (loader lock): it spawns a thread, waits for a live
`UWorld`, flips `GIsClient`/`GIsServer`, then travels to `Station_Prime_P`.

### A2EntitlementPatch: clients quitting on join

A client that joins the server connects **successfully** and then exits a few seconds
later. The UE log shows the join working and no crash at all:

```
LogNet: UPendingNetGame::SendInitialJoin: Sending hello. RemoteAddr: 127.0.0.1:7777
LogNet: Welcomed by server (Level: /Game/A2/Maps/Station_Prime/Station_Prime_P, ...)
LogGlobalStatus: UPendingNetGame::TravelCompleted Pending net game travel completed
   ... ~4 seconds of normal play ...
LogA2MothershipAuthStateMachine: Error: Could not verify entitlement status:
  Missing entitlement for 23916854551246326 (1971031).
  A Shipping build would exit at this point
Closing by request
LogExit: Game engine shut down
```

The Oculus platform runtime cannot prove the logged-in account owns app
23916854551246326 for this build, and the shipping build treats that as fatal. Nothing to
do with the server or the payload — the server only initialises the platform subsystem and
never runs the auth state machine, which is why it is unaffected.

`A2EntitlementPatch` flips one byte in the entitlement result handler
(`A2MothershipAuthStateMachine.cpp`, function at RVA `0x53DFC70`):

```
0x053DFCC4  test bpl, bpl      ; 40 84 ED   bSuccess?
0x053DFCC7  jne  0x053DFD22    ; 75 59      -> entitled path, auth continues
0x053DFCC9  ...                              not-entitled path: log, then exit
```

`75` → `EB` makes the jump unconditional, so the handler always takes the entitled path
and nothing requests an exit. It is guarded by a 16-byte signature that occurs exactly
once in this executable; on any other build the mod logs a mismatch and writes nothing.

It ships as a UE4SS **native** mod (`Mods\A2EntitlementPatch\dlls\main.dll`) so it loads
automatically with every client — no injector, no launcher. It deliberately does not use
the `CppUserModBase` C++ mod API: it exports `start_mod` / `uninstall_mod` (without them
UE4SS unloads the DLL), does the patch in `start_mod`, and returns `nullptr`. UE4SS guards
every mod callback with `if (m_mod)`, so a null return means it never calls back in — and
nothing here depends on the UE4SS ABI, so a UE4SS update cannot break it.

Build it with the solution (or `msbuild A2EntitlementPatch\A2EntitlementPatch.vcxproj
/p:Configuration=Release /p:Platform=x64`) — it outputs straight to
`ue4ss-mods\A2EntitlementPatch\dlls\main.dll`, then `Install-Mods.ps1` deploys it. It logs
to `%TEMP%\A2EntitlementPatch.log`:

```
[A2EntitlementPatch] loaded. game base = 0x7FF6B1760000
[A2EntitlementPatch] patched RVA 0x53DFCC7: jne -> jmp (a failed entitlement check no longer exits the game)
```

Harmless on the server, which patches the same byte and never executes it.

### UE4SS had to be upgraded first

The installed **UE4SS v3.0.1** (Feb 2024) could not initialise on this build. Its
patternsleuth scan resolved everything except `FText::FText(FString&&)` and then retried
in a loop until it gave up — so no mod, including the stock console enabler, ever ran:

```
[PS] Found EngineVersion: 5.4 ... GUObjectArray ... GMalloc ... FName::ToString ...
[PS] Failed to find FText::FText(FString&&): expected at least one value
[PS] Scan failed                      (x69, then it stops trying)
```

Replaced with the **experimental build `v3.0.1-1108-g68caddcf`** (Dec 2024), which scans
this UE 5.4.2 binary cleanly (`PS scan successful`) and loads mods. Note the newer layout:
everything now lives in `A2\Binaries\Win64\ue4ss\`, with only `dwmapi.dll` beside the exe.

The previous install (both copies, plus its Mods folder) is backed up under
`backup\ue4ss-v3.0.1-<timestamp>\` — restore from there to go back.

One harmless warning remains: `Failed to find ConsoleManagerSingleton: found 2 unique
values`. That only affects UE4SS's cvar access, not the console.

### mods.txt: BPModLoaderMod must stay off

With the stock mod set enabled the game dies on every launch:

```
Unhandled Exception: EXCEPTION_ACCESS_VIOLATION reading address 0x0000000000000008
[Callstack] UE4SS.dll ... A2-Win64-Shipping.exe   (from the engine tick)
```

Bisected mod by mod: **`BPModLoaderMod` is the cause.** With it off the game runs
indefinitely; with it on it crashes within a second of mods starting. `Install-Mods.ps1`
disables it (`-KeepBPModLoader` to override). The cost is that BP / LogicMods mods do not
load — nothing else is affected.

The stock `ConsoleEnablerMod` is also disabled, but only because `A2ConsoleUnlock`
replaces it; two mods fighting over the same viewport console is asking for trouble. It
does not crash the game.

## Starting a server

```powershell
cd tools
.\Start-Server.ps1                  # launch + inject + wait for the game port
.\Start-Server.ps1 -Build           # rebuild the DLL first
.\Start-Server.ps1 -Instances 3     # three servers on 7777 / 7778 / 7779
.\Start-Server.ps1 -Status          # pids, uptime, RAM, bound ports
.\Start-Server.ps1 -Stop            # stop them all
```

Settings live in `tools\server.config.psd1` — game path, engine args, the `-Dashboard*`
values, `-RegisterIp`, an optional `-LoadGamemode`, and the log directory. Copy it to
`server.vps.psd1` (or anything else) and pass `-Config server.vps.psd1` to keep several
environments side by side.

What it does: launches `A2-Win64-Shipping.exe` headless with the configured arguments
(stdout/stderr to `tools\logs\server-<stamp>.out.log`), waits `InitWaitSeconds`, injects
`HalcyonA2.dll`, then waits for the process to bind its UE game port and reports it.

Readiness is measured by the bound UDP port rather than by reading the payload log:
`dllmain.cpp` opens `%TEMP%\HalcyonA2.log` with `_wfopen_s`, which is exclusive, so that
file is locked for the lifetime of the process. It is readable once the server stops.

Running several instances is supported: UE takes 7777 and increments when the port is
taken, and the payload registers whichever port it actually bound, so each instance
publishes its own `ip:port`. Each also gets `-DashboardDeploymentId=<id>-<n>` so they do
not collide in the backend.

## Client backend URLs (a2urlpatch.py)

Where the two backend URLs actually live in build 20996 — neither is a plain string in
the `.obb`, which is why a hex search of it comes up empty:

| | Location | Storage |
|---|---|---|
| **Mothership** | pak entry `A2/Config/DefaultEngine.ini`, `[OnlineSubsystemMothership] BaseUrl = "https://aa-mothership.com"` | **Oodle-compressed** inside the pak |
| **Dashboard** | compile-time constant beside `StationDashboardConstants.h`: `https://api.oriondrift.net` | plain string in the game binary — `lib/arm64-v8a/libUnreal.so` (Android) / `A2-Win64-Shipping.exe` (PC) |

`tools\a2urlpatch.py` finds and rewrites both, and every write it makes is
size-preserving: the container keeps its exact byte length, no pak entry moves, and the
replacement string must be the same length as the original.

```powershell
cd tools
python a2urlpatch.py list  ..\..\main.33694970.com.AnotherAxiom.A2.obb --filter Config/
python a2urlpatch.py find  ..\..\main.33694970.com.AnotherAxiom.A2.obb aa-mothership.com
python a2urlpatch.py patch ..\..\main.33694970.com.AnotherAxiom.A2.obb `
       --old "https://aa-mothership.com" --new "http://10.0.0.5:8080/aaaa"      # dry run
python a2urlpatch.py patch ... --write                                          # apply
python a2urlpatch.py patch-bin libUnreal.so `
       --old "https://api.oriondrift.net" --new "http://192.168.1.9:9000/xx" --write
python a2urlpatch.py verify ..\..\main.33694970.com.AnotherAxiom.A2.obb
```

It reads the `.obb` (a zip of STORE'd entries) in place — no extract/repack — parses the
UE5 pak index (v8-v11), and transparently decompresses Oodle entries so `find` can search
inside them.

### How a compressed entry is patched without changing any size

Oodle has no free encoder, so a patched entry cannot be re-Oodled. It is re-encoded with
**Zlib**, which UE supports natively for pak entries:

1. decompress every block (Oodle, via the open-source `ooz`)
2. replace the string — same length, so the uncompressed size is unchanged
3. re-compress each block with zlib
4. write the blocks into the entry's own footprint plus the padding slack that follows it
5. fix up, all fixed-width so nothing shifts: the entry header (Size, block ranges, method
   index, SHA1), the encoded record in the pak index, the footer's compression-method
   table (`Zlib` goes in a free 32-byte slot), the footer's index SHA1, and the zip CRC32
   of the pak inside the `.obb`

Verified end to end on a copy of the PC pak, patched through a zip container:

```
plan    : re-encode as Zlib  16,520 -> 17,465 bytes (budget 18,343 = entry 16,520 + slack 1,823)
container size: 35,467,513 -> 35,467,513 (unchanged)
zip CRC32 updated -> 0x805677E4      python zipfile testzip: OK - all entries valid
pak index hash : OK                  entry hashes: 2519/2519 OK
```

`verify` re-checks all of that on demand: every entry hash is the SHA1 of its stored
(compressed) payload, the footer hash is the SHA1 of the index, and the obb CRC is
recomputed from the entry bytes.

### The Android OBB has no room

Zlib costs ~6% more than Oodle on this ini (16,540 → 17,470 bytes), and the Android pak is
packed with **zero** padding — no gaps anywhere, `index@0x1F1B8D2` starts immediately after
the last entry. So the Mothership URL cannot be rewritten in the Android `.obb` without
changing sizes, and the tool refuses rather than corrupting it. The PC pak is aligned to
0x800 and has 1,823 bytes of slack after that entry, so it patches cleanly.

For the Quest client, override the value at runtime instead — a `Saved/Config` `Engine.ini`
(or `-ini:` on the command line) wins over the packaged `DefaultEngine.ini` and touches no
game file:

```ini
[OnlineSubsystemMothership]
BaseUrl="http://your.server:8080"
```

Worth confirming on device before relying on it. The Dashboard URL has no such problem —
it is a plain string in the binary and `patch-bin` rewrites it in place.

### Oodle

`tools\Build-Ooz.ps1` builds `tools\oodle\ooz.dll` from the open-source clean-room Kraken
decompressor (`powzix/ooz`) plus the small ctypes wrapper in `tools\oodle\oozdll.cpp`.
Nothing proprietary is redistributed, and only decompression exists — which is exactly why
patched entries come back as Zlib.

## Building a redirected client (build_client.py)

Turns a stock APK + OBB into a client pointed at your own backend. Run it with no
arguments (or double-click `tools\Build-Client.cmd`) and it just asks:

```
cd tools
python build_client.py
```

```
A2 client builder
Point a stock Orion Drift client at your own backend.
Press Enter to take the [default] on any question.

    The APK holds the Dashboard URL, inside libUnreal.so.
      1) A2-Android-Shipping-arm64.apk   (81 MB)
         C:\Users\Zern\Documents\OrionDriftStuff
      s) skip - do not touch this file
? which APK? [1]:
? new Mothership URL: http://10.20.30.40:8080
? use the same host for the Dashboard (http://10.20.30.40:8080)? [Y/n]:
? switch the OBB check off completely? [y/N]:
? install to a connected headset when finished? [y/N]:
? build it? [Y/n]:
```

It finds the APK and OBB lying around near the tool and offers them by number; a typed or
drag-and-dropped path works too, and `s` skips a file. Each question explains itself and
every answer has a default. When it finishes it prints the equivalent one-line command, so
the same build can be repeated without the questions:

```powershell
python build_client.py --apk ..\..\A2-Android-Shipping-arm64.apk `
                       --obb ..\..\main.33694970.com.AnotherAxiom.A2.obb `
                       --mothership http://192.168.1.50:8080 `
                       --dashboard  http://192.168.1.50:9000 `
                       --out ..\..\clientbuild
```

It finds `zipalign`, `apksigner`, `keytool` and `adb` on its own — including the copies
Unity ships with its Android player, which is where they came from here, so nothing extra
had to be installed. A debug keystore is generated on the first run. Add `--install` to
push straight to a connected headset.

What it does:

| Step | |
|---|---|
| **OBB** | Rewrites `[OnlineSubsystemMothership] BaseUrl` in the packaged `DefaultEngine.ini`, re-encodes that pak entry as Zlib, relocates it to the end of the pak's data region, repairs the index/footer/hashes, and rebuilds the `.obb`. The Mothership URL can be **any length**. |
| **APK** | Rewrites the Dashboard URL inside `lib/arm64-v8a/libUnreal.so`. That one is patched in place in the binary, so it must be **no longer** than `https://api.oriondrift.net` (26 chars); it is NUL-padded if shorter. |
| **APK** | Retargets the expected OBB size compiled into `classes.dex` (see below), then repacks, zipaligns and re-signs. |

Because the whole pak is rebuilt rather than edited in place, the strict same-size rule
that `a2urlpatch.py` works under no longer applies — that tool is still the right one for
surgical, size-preserving edits.

### The OBB size check

The app will not accept an expansion file whose length differs from the one it was built
with. Two pieces are involved, and neither is in a native library:

| Piece | Where | Role |
|---|---|---|
| the expected size | `classes.dex`, a `const-wide/32` literal = 1,515,461,948 | what the length is compared against |
| the on/off switch | `AndroidManifest.xml` meta-data `com.epicgames.unreal.GameActivity.bVerifyOBBOnStartUp` = true | whether the check runs at all |

The size lives in UE's generated `OBBData` class, which R8 renamed - confirmed by walking
the dex rather than by guessing at a byte match:

```
Lcom/AnotherAxiom/A2/a;-><clinit>     builds the XAPKFile[] table and stores it in a
Lcom/AnotherAxiom/A2/a$a;             the record: boolean a, String b, long c  <- the size
    const-wide/32 v4, 1515461948      exactly the stock OBB's byte length
```

`libUnreal.so` does **not** validate the OBB. What it does contain is
`bDisableVerifyOBBOnStartUp`, `bAllowLargeOBBFiles`, `bForceSmallOBBFiles`,
`bAllowPatchOBBFile`, `bAllowOverflowOBBFiles` - reflected `AndroidRuntimeSettings`
property names - plus `assets/main.obb.png` and `assets/patch.obb.png`, the paths used
when data is packaged inside the APK. Those are packaging-time settings: the packaged
`DefaultEngine.ini` has `bDisableVerifyOBBOnStartUp = False`, which is exactly why UBT
emitted `bVerifyOBBOnStartUp=true` into the manifest. Changing the ini in a built client
does nothing, because the decision was already baked into the manifest at package time.

`build_client.py` retargets that literal to the size of the OBB it just produced. The
literal is 32 bits sign-extended to a long, so it covers OBBs up to 2 GiB; `classes.dex`
keeps its exact length and its SHA-1 signature and Adler-32 checksum are recomputed.
`--no-obb-size-patch` skips it, and `--obb-size OLD:NEW` retargets when patching an APK
without rebuilding the OBB in the same run.

`--disable-obb-verify` takes the other route and flips the manifest flag to false, which
skips existence and size checking together. It is a 4-byte `TYPE_INT_BOOLEAN` edit -
verified as exactly four changed bytes, manifest length unchanged. Retargeting the size is
the default because it leaves the check working.

If you rebuild the OBB without also rebuilding the APK, the tool warns you — the pair has
to be built together or the size constant goes stale.

## Runtime arguments

The payload reads these from the game command line (they ride in via the allocator's
`agent.cfg game_args`; environment variables do **not** reach the process):

| Argument | Effect |
|---|---|
| `-DashboardApiUrl=` `-DashboardApiKey=` `-DashboardDeploymentId=` | Read by the game's own station-dashboard path; the deployment id also scopes the per-server Vivox channel |
| `-RegisterIp=<ip>` | Override the auto-detected public IP used for backend registration |
| `-LoadGamemode=<path>` `-GamemodeSlot=<id>` `-GamemodePos=X,Y,Z` | Load a gamemode into a module slot |
| `-SnapToMarker=<substr>` `-GmNudge=X,Y,Z` `-GmRewriteRot` `-SpawnSlotAtMarker` `-SlotRot=P,Y,R` | Gamemode placement |
| `-BallClass=<class>` | Replaceable ball class |
| `-NoFixLOD` | Disable the `DefaultLODSettings` pop-in fix |
| `-QuietSims` | A/B: disable all ball-sim network sends (player-lag test) |

The backend hosts and the Vivox credentials are compile-time constants near the top of
`dllmain.cpp` (`kBackendHost`/`kBackendPort`, `kMotherHost`/`kMotherPort`, `kServerApiKey`,
`kVoipIssuer` and friends). Change them there.

Runtime logging goes to the allocated console **and** `%TEMP%\HalcyonA2.log`.

## Re-dumping after a game update

```powershell
cd tools
.\Get-Dumper7.ps1
.\Dump-A2.ps1
.\Build.ps1
```

If the game binary itself changed, expect the build to still succeed while the DLL misbehaves at
runtime — the RVA constants in `dllmain.cpp` are the part that must be re-reversed by hand.
`C:\Dumper-7\<dump>\IDAMappings\` and `GObjects-Dump-WithProperties.txt` are the starting points.
